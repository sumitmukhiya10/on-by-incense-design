# ON BY INCENSE DESIGN

The website uses HTML, CSS, vanilla JavaScript, FastAPI, and private JSON files. The same FastAPI server serves the customer pages, admin page, uploaded images, and API.

## Start the website

To prepare the environment automatically on Windows, double-click `start-server.bat`. It creates the virtual environment if needed, installs the listed packages, and starts the website. Keep the terminal window open while the site is running, then open the printed `http://127.0.0.1:8000` address. Do not open `index.html` directly or use Live Server: the API requests must go to the Python server.

To start it manually from the project folder, run:

```powershell
python -m pip install -r requirements.txt
python -m uvicorn server:app --reload
```

Then open <http://127.0.0.1:8000>. The admin page is <http://127.0.0.1:8000/admin.html>.

If Windows says it cannot find Python, install Python 3.12 or newer and enable **Add Python to PATH**. If you have already created this project's virtual environment, use:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn server:app --reload
```

## First-time admin setup

1. Start the server and leave its window open.
2. Open <http://127.0.0.1:8000/admin.html>. The first visit shows **Create Admin Password**.
3. Choose a strong Admin password and a different strong master recovery password. Each must have at least 12 characters, with upper and lower case letters, a number, and a symbol.
4. Copy the one-time backup code shown after setup and keep it somewhere private. It is not saved in plain text and cannot be shown again.
5. The dashboard opens after setup. Future visits use the password-only login. If the Admin password is forgotten, choose **Forgot your password?** and use the master recovery password to set a new one. While signed in, the **Change Password** page also has a recovery option.

Local first-time setup does not need a code. If you are setting up through a remote reverse proxy, use `/admin-setup.html` and the one-time code printed in the server window. The one-time backup code is a fallback and is replaced after use. Admin and master recovery passwords are stored as server-side hashes.

## Where the store keeps data

- `json/products.json`, `settings.json`, and `discounts.json` hold the public catalog and store settings.
- `json/orders.json` and `enquiries.json` hold private customer requests. They are not served as website files.
- `json/admin.json` contains Admin, master recovery, and one-time backup-code **hashes**, never the passwords or backup code.
- `images/products/` and `images/homepage/` hold photos uploaded from the admin page. Existing photos remain in `images/`.
- Each saved JSON file gets a `.bak` copy of its previous contents.

Use the **Choose file** controls in the admin page. Supported images are JPG, PNG, and WebP, up to 15 MB each. Uploaded image names are generated by the server. Deleting a product never deletes its photos.

Checkout saves a pending order request with server-calculated prices and discounts, then opens WhatsApp so the customer can send it to the showroom. Contact messages are saved as enquiries and also open WhatsApp. The WhatsApp number is editable in **Store Details**.

## Deploy on Railway

The customer pages, admin page, images, and `/api/` endpoints run together in one FastAPI service. `Dockerfile` starts the app in production without `--reload`. Railway should mount a persistent volume at `/data`; the app stores mutable data in `/data/json/` and images in `/data/images/`. The paths can be changed with `STORAGE_DIR`, `DATA_DIR`, and `IMAGE_DIR`.

### 1. Keep private data out of GitHub

`json/`, `.env`, local backups, temporary files, and tests are excluded from Git and the Docker build. Only `seed_data/products.json`, `seed_data/settings.json`, and `seed_data/discounts.json` are included as safe starting store data. `orders.json`, `enquiries.json`, and `admin.json` are never copied into the Docker image.

Before pushing, check that the private files are ignored:

```powershell
git check-ignore json/admin.json json/orders.json json/enquiries.json .env
```

If any private file was already committed to GitHub, `.gitignore` alone does not remove it from Git history. Remove it from the repository and its history, rotate affected passwords, and handle any exposed customer data before deploying.

### 2. Create the Railway service and volume

1. Push this project to a GitHub repository and create a Railway project from that repository. Keep the repository private if you do not want public product photos or shop settings exposed as source files.
2. Use the repository root as the service root. Railway detects the `Dockerfile` and builds the single service.
3. In the service's **Volumes** section, create and attach a volume with mount path **`/data`**. Railway sets `RAILWAY_VOLUME_MOUNT_PATH` automatically. Keep **one replica**: Railway volumes do not support replicas, and the JSON store is designed for one running instance.
4. In the service's **Variables** section, add:

   | Variable | Value |
   | --- | --- |
   | `APP_ENV` | `production` |
   | `STORAGE_DIR` | `/data` |
   | `SESSION_SECRET` | A random secret with at least 32 characters; generate one as shown below. |
   | `INITIAL_ADMIN_PASSWORD` | A new strong owner password, 12+ characters with upper/lowercase, a number, and a symbol. |
   | `INITIAL_MASTER_PASSWORD` | A different strong recovery password with the same requirements. |

   Do not use `admin123`. Do not put real values in `.env.example`, `Dockerfile`, or GitHub. Generate the session secret on your computer with:

   ```powershell
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

   Set the generated value directly in Railway's Variables screen. Keep `SESSION_SECRET` for every deployment. After the first successful deployment, remove `INITIAL_ADMIN_PASSWORD` and `INITIAL_MASTER_PASSWORD` from Railway Variables; the saved password hashes on the volume will keep working, and later deploys will not reset the account.

   You can leave `DATA_DIR` and `IMAGE_DIR` unset; they default to `/data/json` and `/data/images`. Set them only if you intentionally want different paths within the mounted volume.

### Reset an already initialized Railway admin

If an existing production admin password is not working, update `INITIAL_ADMIN_PASSWORD` and `INITIAL_MASTER_PASSWORD` in Railway Variables, then temporarily set `RESET_ADMIN_FROM_ENV=true` and redeploy using the same volume. The server validates both values, stores new password hashes in `/data/json/admin.json`, and clears active sessions. It does not change products, orders, enquiries, images, discounts, or store settings. Passwords and hashes are never written to logs.

The reset is recorded in the existing admin file so leaving the flag on cannot reapply those values after the owner changes passwords. After confirming the new Admin and master recovery passwords work, set `RESET_ADMIN_FROM_ENV=false`, remove both `INITIAL_*_PASSWORD` variables, and redeploy. This clears the one-time reset marker without changing the saved credentials. To trigger another reset later, first deploy once with the flag false, then set new values and turn it true.

### 3. Set startup and health check

The Dockerfile uses this production command, with Railway's `PORT` expanded at runtime:

```sh
uvicorn server:app --host 0.0.0.0 --port $PORT
```

The `:app` is required because `server.py` defines the FastAPI object as `app`. In Railway service settings, set the health check path to **`/api/health`**, then deploy. The app refuses production startup if the volume, session secret, starting public JSON, or first admin passwords are missing. Admin passwords are hashed before saving; production session cookies are `HttpOnly`, `SameSite=Strict`, and `Secure`.

Leave Railway's dashboard **Start Command** override blank so the Dockerfile command runs. If you choose to override it, use `/bin/sh -c "exec uvicorn server:app --host 0.0.0.0 --port $PORT"` so the container shell expands `PORT`. Set the restart policy to **On Failure** and keep one replica.

### 4. Preserve existing store data

The public starting catalog is copied from `seed_data/` into the volume only when its destination file does not exist. Original files in `images/` are copied into `/data/images/` only when the matching destination image does not exist. Existing volume data and admin-uploaded images are never overwritten. Product image URLs remain `/images/...`, so uploaded photos keep stable public URLs across deploys.

To bring over existing private customer orders and enquiries, upload them directly to the Railway volume; do not add them to GitHub. Before the first live launch, install and log in to the Railway CLI, link the project, and find the volume name:

```powershell
railway login
railway link
railway volume list
railway volume files upload .\json\orders.json /json/orders.json --volume <volume-name>
railway volume files upload .\json\enquiries.json /json/enquiries.json --volume <volume-name>
```

Run the upload commands from this project folder and replace `<volume-name>` with the name shown by `railway volume list`. The upload source files stay on your computer and are not sent through GitHub. Do this before accepting live orders. If the Railway store has already received new orders or messages, download a volume backup and merge records instead of replacing those files. The new admin account is created from the two Railway password variables; the local `admin.json` is not part of the deploy.

### 5. Verify the live service

After Railway reports the deployment healthy, open the generated public domain and check `/api/health`, the home page, Shop, a product page, cart quote, contact form, and WhatsApp checkout. Then log in to `/admin.html`, add a test product/photo, change a setting, and confirm both remain after a redeploy. Remove test records and photos before opening the shop to customers.

Railway's volume is persistent, but it is not a substitute for backups. Configure volume backups in Railway and download periodic copies of `/data/json/` and `/data/images/` to a separate secure location. A mounted volume prevents ordinary deployments from replacing saved data; it does not protect against deletion, a full disk, or account loss.

## Backups and local deployment

The pre-backend website JSON was copied to `tmp/pre-fastapi-backup-20261112/data/` before migration. Older Supabase and Cloudflare materials remain in `tmp/legacy-backend-archive/`; they have not been deleted or modified.

For local development, the app continues to use the existing project `json/` and `images/` folders unless environment variables are set. Back up those folders regularly and keep the backup outside the website's public files. Do not host the site on a static-only service: product edits, file uploads, orders, enquiries, and secure admin access require the FastAPI process to remain running with writable storage.
